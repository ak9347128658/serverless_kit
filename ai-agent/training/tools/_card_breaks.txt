# Concept: TypeScript and Node packaging || pskit compiles `.ts` files with `tsc` when it packages or runs the service. It uses `node_modules/.bin/tsc`, then `tsc` on `PATH`, then `npx --yes -p typescript@5 tsc`. TypeScript is detected from a `tsconfig.json` or a `.ts` handler. `package.node.typescript` true or false forces it. With a tsconfig, pskit extends it and only overrides `outDir`, `rootDir`, and `noEmit: false`. Without one it compiles to CommonJS / ES2022. Type errors fail the build. --- concept-variables
# Concept: config variables || pskit resolves four variable forms in the config. `${env:NAME}` is an environment variable and is an error if unset. `${env:NAME, default}` uses `default` when it is unset. `${opt:stage}`, `${opt:provider}`, and `${opt:region}` are the effective CLI values. `${opt:x, default}` is allowed. `${self:dotted.path}` reads the merged config, for example `${self:service}` or `${self:custom.table}`. `${file(path.json)}` reads a file relative to the config. `.json` and `.yml` are parsed. Other files are stripped text.

--- onprem-database-replicas
## Databases: one server, or a primary with read replicas - **Single server**: one || container on this machine or a server. To scale it up, give that server more CPU and memory (vertical scaling). Nothing else changes. - **Primary + read replicas** (horizontal scaling): the **primary** takes every write, each **read replica** on another server keeps a copy and answers reads, and an optional **load balancer** gives the functions one address that sends writes to the primary and reads to the replicas. Add replicas later as reads grow. You only pick the servers: which one writes (the primary), which ones read (the replicas) and which one runs the load balancer. Save them first (**Servers**, below). pskit installs Docker where it is missing and sets up replication for each engine: | Engine | Replication | *Synchronous* means | Load balancer (one address) | |---|---|---|---| | PostgreSQL | streaming replication (WAL), each replica starts from `pg_basebackup` | `synchronous_standby_names = 'ANY 1 (*)'`: a commit waits until one replica has it on disk | pgpool-II, port 6432 | | MySQL | GTID replication; a replica copies the databases, then follows | semi-synchronous: a commit waits for one replica (async again after 10 s without one) | ProxySQL, port 6033 | | MariaDB | GTID replication, as MySQL | built-in semi-synchronous, as MySQL | ProxySQL, port 6033 | | MongoDB | replica set (`rs_<key>`), members share a generated key file | write concern `w: majority` | none: the driver routes from one replica set URL | **Asynchronous** (default) is the fastest: the primary commits at once and replicas follow a few milliseconds behind, so a crash of the primary can lose the last writes. **Synchronous** loses no committed write, at the cost of a round trip to a replica per commit. PostgreSQL waits while no replica is connected, so keep at least two replicas with *sync*. The load balancer sends writes, transactions and `SELECT ... FOR UPDATE` to the primary and plain reads to the replicas, and falls back to the primary only when no replica is up. Without a load balancer, the functions' `URL` is the primary and the replicas are listed in `READ_URLS`. The form draws the result as you pick (functions → load balancer → primary → replicas, solid lines for sync, moving dashes for async). **Details** shows the same picture with each member's state, every replica's lag, what the primary reports (`pg_stat_replication`, `SHOW REPLICAS`, `rs.status()`), and **+ Add read replica** / **Remove**.

--- onprem-placement
# Functions on several servers (on premises) By default every function of a || project runs in one host: on one machine, or on every server of a cluster. **Placement** splits them: each group of functions runs on its own server (or cluster), with only its own code and dependencies, and the groups work together as one project. Per group: one of `server`, `cluster` or `local: true` (the default group may leave it out and use `options.deploy` / `--server` as before), `functions`, and optionally `port` (needed when two groups share a server) and `advertise` (the URL the other groups call, when the server's own address is not reachable). The studio's **Deploy** page has the same editor ("Where functions run"), and each function shows where it runs.

--- onprem-placement
## Each function is its own sub-project Create functions in their own folder with || their own dependencies: The studio does this for new functions ("Own folder with its own requirements.txt"). A function's sub-project is the nearest folder above its handler with a `requirements.txt` (Python) or `package.json` (Node.js). * Every cloud: the sub-projects' requirements are added to the bundle, so the code runs unchanged anywhere. * On premises with placement: **each server installs only the requirements of its functions**, and the folders of functions placed elsewhere are left out of its bundle. Two functions on one server that pin conflicting versions fail the deploy with a clear message: place them on different servers. * Node.js sub-projects get their own `node_modules` in their folder, so each function resolves its own versions.

--- onprem-placement
### Functions that share a code file Each server's copy of a shared code file holds || only the handlers of its own functions: pskit removes the others (and the imports only they used) from that group's bundle; your source is not changed. Module-level helpers stay. `pskit_host.json` on the server lists what was removed (`stripped`). Moving them to their own folders is still cleaner, and gives each its own requirements: Functions whose handlers sit side by side in one file (`app/handlers.py` with `hello`, `get_item`, `create_item`, as `pskit init` makes them) are shared code. Validation warns when they are in different groups. Split them: The function, the module-level helpers and imports it uses (relative imports made absolute) move to `functions/<name>/handler.py`. Its `requirements.txt` gets the lines of the project's `requirements.txt` that its imports name, and its handler in `pskit.yml` is updated.

## Redis / Valkey stream (`redis_stream`) A stream with a consumer group instead || of a list: native leases and delivery counts, several hosts can share one group, and other services can read the same stream with groups of their own. Needs Redis 6.2+ or Valkey. Messages are `XADD jobs * body <text> attributes <json>`; another producer may `XADD` any fields (the `body` field, else the first field's value, becomes the record body). An entry is acknowledged and deleted once the handler succeeded. A failed entry is claimable again at once; after `max_receive` deliveries it goes to `dead_letter`. An entry a crashed host never settled is taken over (`XAUTOCLAIM`) once it has been idle for `visibility_timeout`.

# On-premises storage (`type: storage`) Run functions when files appear in a || bucket, and read or write objects: the host's built-in buckets, a shared folder, MinIO or another S3-compatible store, or a bucket in a cloud (S3, R2, Azure Blob, GCS, ...). The host lists each watched bucket every `poll_seconds` and compares ETags: a new or changed object emits `created`, a missing one `deleted`. Objects already there at the first start are recorded, not emitted.
