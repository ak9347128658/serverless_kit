# Example: 19-custom-drivers

This directory is one of the examples that tests/test_examples.py packages and runs locally because it contains pskit.yml. Files here include README.md, pskit.yml, requirements.txt. Comments in pskit.yml: Custom on-premises drivers: your own class feeds a queue or storage trigger. `driver: custom` + `class: "<module>:<Class>"` loads a class from this app. Every other option is passed to its constructor (`<name>_env: VAR` reads VAR from the host's environment first, so secrets stay out of generated files). Template drivers wrapping client libraries (add the library to requirements.txt): events: type: queue external: true options: {driver: custom, class: app.rabbitmq_queue:RabbitQueue, url_env: RABBITMQ_URL, queue: events} orders: type: queue external: true options: {driver: custom, class: app.kafka_queue:KafkaQueue, bootstrap_servers: "kafka:9092", topic: orders, group_id: workers} On a cloud the same resources are plain external queues / buckets (the custom classes are on-premises only); these blocks just make `--provider` switch cleanly.
# 19 · Custom on-premises drivers

When the queue or storage you already run has no built-in driver, write a small class and point a resource at it. The on-prem host still does the rest: polling, batching, `BatchResult` retries, dead-lettering, logs, stats and the dashboard. | Resource | Class | Backed by | | --- | --- | --- | | `jobs` | `app.backends:SqliteQueue` | one SQLite file, table `jobs` | | `jobs-dlq` | `app.backends:SqliteQueue` | the same file, table `jobs_dlq` | | `inbox` | `app.backends:FolderStorage` | a folder (works for NFS / SMB shares) | `app/rabbitmq_queue.py` (pika) and `app/kafka_queue.py` (kafka-python) are templates for brokers that need a client library. Both deliver at least once.
## The contract A **queue** class implements: | Method | Called | Must | | --- |

--- | --- | | `submit(body, attributes) -> id` | `submit_queue()`, `POST /__pskit/queues/<name>`, dead-lettering | store one message | | `claim(batch, visibility, now) -> [msg]` | every poll | reserve up to `batch` messages for `visibility` seconds; each `msg` has `id`, `body`, `attributes`, `receives`, `enqueued_at` (+ private `_keys` you need later) | | `settle(claimed, failed_ids, max_receive, dead_letter, now)` | after the handler | delete successes; make failures visible again; when `receives + 1 >= max_receive` and `dead_letter` is given, `dead_letter.submit(...)` then delete | | `depth() -> int` | stats / dashboard | messages waiting, or `-1` if unknown | | `recover(now, visibility)` | every few seconds | release reservations a crash left behind (no-op if the broker does it) | A **storage** class implements `scan() -> {key: (etag, size)}`, `put(key, data)`, `get(key) -> bytes` and `delete(key) -> bool`. The host diffs consecutive scans to fire `created` / `deleted`, so `etag` must change whenever the content changes.
